# 房主开始与整场计时调整

更新：2026-10-04。适用页面：p.html。本轮覆盖历史文档的开房计时和前端手动暂停、继续、关闭规则。

## 前端已完成

- 房主菜单仅保留首次「开始游戏」，删除暂停、继续、关闭入口、确认弹框和对应命令发送逻辑。
- 首次开始沿用 `{"type":"START_HAND","requestId":"uuid","payload":{}}`，由服务端授权和验证房主、人数、准备与筹码条件。无需新增计时命令，也不向 payload 增加时间字段。
- 点击开始、等待确认、操作失败均不在本地创建截止时间。前端只根据 `room.timing.endsAt` 和 `serverTime` 显示剩余时间。
- `timing.status=WAITING` 且 `endsAt=null` 时显示「等待房主开始游戏」，房间详情的结束时间显示「开始游戏后确定」。开始成功后服务端广播 OPEN 及绝对截止，前端立即显示倒计时。
- 刷新、重连和新成员进入沿用同一个截止，不重置时长。每手的行动倒计时与下一手结算展示倒计时继续按原协议工作。
- 兼容旧服务真实返回的截止及结束快照；前端不能通过隐藏或延后旧 endsAt 改变服务端关房行为。历史停止状态显示等待服务端继续，无法从当前页面手动恢复。

## 后端需要调整（本仓库未实现）

现有后端能力文档规定 `endsAt=createdAt+durationMinutes`。从房主开始游戏计时需要 Java 服务改变首次开局事务，前端无法单独完成实际生效。

1. 开房仅保存 `createdAt` 和 `durationMinutes`，`startedAt/endsAt=null`，输出 `timing.status=WAITING`。未首次开始的房间不进入时长到期扫描，但活动结束或取消仍复用现有结束流程。
2. 在首次 `START_HAND` 验证通过、发牌成功的同一房间锁和事务内，用服务端时间设置 `startedAt=now`、`endsAt=now+durationMinutes`，持久化首次开始标记、手牌、计时和 revision，提交后广播完整 SNAPSHOT。失败回滚，不能先开计时再返回开局失败。
3. 后续自动开手、重试、重复 requestId、刷新、重连、新成员进入均不能改写 startedAt/endsAt。并发首次开始只允许一个事务成功，复用已有去重与房间行锁。
4. entry、rooms、SNAPSHOT 输出一致的 timing 与 serverTime。尚未开始示例：

   ```json
   {"room":{"playState":"WAITING","timing":{"status":"WAITING","startedAt":null,"endsAt":null,"endedAt":null,"reason":null}}}
   ```

   首次成功示例（durationMinutes=120）：

   ```json
   {"serverTime":"2026-10-04T02:00:00Z","room":{"playState":"RUNNING","timing":{"status":"OPEN","startedAt":"2026-10-04T02:00:00Z","endsAt":"2026-10-04T04:00:00Z","endedAt":null,"reason":null}}}
   ```

5. 到期仍完成当前手，再冻结最终报告并关房；自动续局和人数恢复必须检查同一个持久截止。取消手动入口不影响服务端到期、活动取消或其它已发生的结束通知。
6. 已开始的旧房间保留原截止，避免延长正在进行的场次。未开始的旧房间如需改为等待计时，须按可靠的首次开始记录一次性迁移；没有记录时不能从客户端状态猜测。已有 PAUSED 房间须由服务端处理恢复或结束，当前前端没有恢复入口。

## 验收

- 开房等待超过配置时长仍可首次开始；活动结束时仍按原生命周期拒绝。
- 普通成员、人数不足、准备不足或发牌失败的 START_HAND 不开始计时；成功时截止恰为 startedAt 加时长。
- 两个房主客户端并发点击、重复请求、重启恢复均只开始一次且不延长截止。
- 两个客户端、刷新及后来进入者看到相同截止；本机时钟偏差通过 serverTime 校准。
- 到期的当前手正常 ACTION/超时和结算，禁止新手，最终关房后按原规则展示报告。

前端模拟接口测试已覆盖等待、点击后仍等待确认、服务器时间校准、重复快照、刷新沿用截止及到期结算；真实后端起点调整尚需联调。
